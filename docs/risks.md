# Risques architecturaux identifiés

> **Mise à jour (audit architectural du 2026-09-06)** : voir [audit-2026-09.md](audit-2026-09.md) pour le détail. Les risques #4 et #6 ci-dessous ont reçu une mitigation concrète (auparavant juste évoqués) ; trois risques ont été ajoutés (#11, #12, #13).

| # | Risque | Impact | Mitigation retenue |
|---|---|---|---|
| 1 | Fuite de données cross-tenant par oubli de scoping | Critique (confiance produit, conformité) | Défense en profondeur à 4 couches, voir [multi-tenancy.md](multi-tenancy.md). Non éliminé à 100% par design seul — nécessite discipline + tests systématiques ([testing.md](testing.md)) |
| 2 | `Shared/` devient un fourre-tout de logique métier au fil du temps | Moyen (érosion de la modularité) | Règle d'équipe explicite ([architecture.md](architecture.md) §4) : `Shared` = contrats et primitives uniquement, appliquée en revue de code ; envisager `deptrac` si le volume de modules grandit significativement |
| 3 | Couplage implicite entre modules via accès direct aux Models d'un autre module | Moyen (empêche l'extraction future d'un module) | Convention de dépendance documentée ([modules.md](modules.md) §"Règles de dépendance"), contrat `Sellable` comme premier exemple ; pas d'outillage automatique au démarrage, à ajouter si des violations apparaissent en pratique |
| 4 | Colonne dénormalisée `products.current_stock` qui diverge du ledger `StockMovement`, en particulier lors de ventes concurrentes sur le même produit (lecture-puis-écriture non sérialisée) | Moyen (données stock incorrectes visibles utilisateur, ou survente) | **Précisé lors de l'audit** : `lockForUpdate()` sur la ligne `Product` à l'intérieur de la transaction qui écrit le `StockMovement` (voir [database.md](database.md) §11), pas seulement "même transaction" comme initialement formulé ; commande artisan de recalcul/réconciliation en défense complémentaire |
| 5 | Système de features/permissions mal synchronisé (une feature existe en base sans middleware réel derrière, ou l'inverse) | Moyen (fonctionnalité visible mais cassée, ou bloquée à tort) | Règle : une `Feature` n'est créée en base qu'au moment où le module correspondant est effectivement implémenté et son middleware branché — jamais en avance de phase |
| 6 | Job asynchrone (queue) exécuté sans `TenantContext` renseigné, car celui-ci est un singleton per-request | Élevé si des jobs métier apparaissent sans cette règle en tête | Documenté explicitement dans [multi-tenancy.md](multi-tenancy.md) §4 ; à rappeler dans la revue de code du premier module introduisant un job (probablement `Notifications` ou `Reports`) |
| 7 | `spatie/laravel-permission` en mode teams : cache de permissions non invalidé correctement lors d'un changement de store en cours de session applicative | Faible à moyen (permissions obsolètes affichées brièvement) | Le contexte est reconstruit à chaque requête HTTP (pas de session longue durée côté serveur), ce qui limite fortement le risque ; à surveiller si un cache applicatif plus agressif est introduit plus tard |
| 8 | Ambiguïté 403 vs 404 pour une ressource hors tenant, non tranchée définitivement dans cette phase | Faible (cohérence UX/sécurité) | Décision explicitement différée à l'implémentation du module `Tenancy`, avec les deux options documentées ([multi-tenancy.md](multi-tenancy.md) §2) — à trancher avant d'écrire le premier test d'isolation pour éviter des tests incohérents entre modules |
| 9 | Croissance du nombre de modules (17 aujourd'hui) rendant `routes/api.php` et `bootstrap/providers.php` difficiles à lire à terme | Faible | Chaque module inclut son propre fichier de routes (`Routes/api.php`) et son propre `ServiceProvider` ; le fichier central reste une liste d'inclusions, pas de logique |
| 10 | Décision de base de données partagée (vs DB par tenant) qui ne scale plus si un très gros client (chaîne à 100+ boutiques) apparaît | Faible à ce stade, à surveiller | Réévaluer uniquement si un cas d'usage concret l'exige ; la structure `store_id` partout rend une migration future vers un sharding par `business_id` possible sans réécriture complète, si nécessaire |

| 11 | Injection de relation inter-tenant via un champ `*_id` non scopé dans une validation `exists` (ex: `customer_id` d'un autre store accepté dans le corps d'une requête) | Élevé (fuite de données, similaire à un IDOR mais indétectable par le scope global ou une Policy classique) | Règle obligatoire ajoutée lors de l'audit : tout `Rule::exists()` sur une ressource tenant-scopée doit être `->where('store_id', ...)` — voir [multi-tenancy.md](multi-tenancy.md) Couche 5 |
| 12 | `store_id` mass-assignable écrasant silencieusement le tenant réel d'une nouvelle ressource | Critique | **Corrigé pendant l'audit** dans le code déjà écrit (`BelongsToStore`), pas seulement documenté — voir [security.md](security.md) §12 |
| 13 | Transferts de stock inter-boutiques non gardés (permission, appartenance aux deux stores, même Business) | Élevé si implémenté sans ces garde-fous | Formalisé comme exception contrôlée et unique dans tout le système — voir [multi-tenancy.md](multi-tenancy.md) §7 |

## Risques explicitement acceptés pour cette phase

- Absence d'outil de vérification statique des frontières entre modules (deptrac ou équivalent) — accepté tant que l'équipe reste petite et la revue de code suffisante.
- Absence de choix définitif de fournisseur de paiement pour les abonnements — accepté, voir [subscriptions.md](subscriptions.md) §5.
- Absence de stratégie multi-devise/multi-langue détaillée — les colonnes (`currency`, préférence de langue utilisateur) existent dans le schéma mais la logique de conversion/traduction n'est pas conçue ici, à traiter si un besoin international concret se présente.
